## Historical controls, with distribution qualification

`historical-reanalysis.json` is generated by:

```sh
python3 tools/g9_count_evidence.py \
  --output docs/runs/2026-09-25-grouped-count/historical-reanalysis.json
python3 tools/g9_count_model.py \
  --output docs/runs/2026-09-25-grouped-count/protocol-model.json
```

The reanalysis reads PR21's `same-backend-toggle.tar.gz`, both write/maintenance
archives and older G9 flat/DSO profiles. Every original archive remains at its
original path. In the final related-write fixture, the historical `rare` and
`selective_and` labels each matched 8,212/25,576 rows. The owner-on CPU medians were
3,735.7 and 2,577.4 microseconds, versus GIN's 2,759.8 and 2,678.3 respectively.
Broad AND/OR owner-on medians were 5,075.5/4,611.0 versus GIN 7,244.2/4,916.5.
These are not grouped COUNT results.

The CPU profiles do not precisely partition each phase. DSO self samples are not
call-chain exclusive timers. New EXPLAIN counters separate copied index payload
bytes from decoded sealed offset payload bytes; they do not fabricate GIN decoder
counts or unmeasured per-phase CPU. See [the architecture and benchmark record](../../g9-grouped-count.md).

## Reproduction and acceptance

Build the exact pinned toolchain with the unchanged Cargo lockfile. Run all native
CI checks and `tools/g9_count_qualification.sh` in normal and test-hook modes, then
the paired harness on an isolated durable PG18.6 server. The default experiment
uses a clean committed source tree, 20,000 and 1,000,000 varied synthetic rows,
old-PIN/new-PIN/GIN in every balanced block, identical PG ranking expressions,
full identity comparisons, source/binary hashes, raw plans and per-sample records.
Actual execution-path counters distinguish grouped runs from correct fallbacks.

Before promotion: close independent visibility/FFI review, native compilation and
recovery gates, real allocation-failure/RSS tests, concurrent writer latency and
throughput, cold cache and broader corpus evidence. Incremental sealed segments,
write amplification and exact-score top-k are still open architecture work. Keep
`pin.enable_grouped_count` off until the relevant correctness gates pass.
